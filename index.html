02 / OBSERVABILITYCloudWatch · S3 · Linux

Application Log Collection & S3 Archival

Improving access to application logs for troubleshooting and longer-term review without relying only on local instance storage.

Application logs→CloudWatch Agent→CloudWatch Logs→S3 archive
Read the engineering approach

Implementation considerations

  • Define log file paths, stream naming, retention, and IAM permissions explicitly; validate the agent configuration before restarting it.
  • Confirm new events arrive in the expected log group and review timestamps, multiline stack traces, and truncation/wrapping behavior.
  • Use a supported export or subscription/streaming design for S3 delivery based on freshness requirements; avoid assuming CloudWatch Logs Insights queries run continuously.

Validation signals

Fresh log events, correct timestamps and streams, expected S3 objects, and an agreed retention/lifecycle policy.

Evidence to attach: redacted agent configuration, log-group view, and S3 object/prefix sample.

04 / TROUBLESHOOTINGNetworking · ALB · Linux

Service Connectivity Investigation

Tracing an application connectivity issue across local listeners, network paths, load-balancer rules, and allow-list configuration.

Reproduce→Test each hop→Check rules→Retest
Read the engineering approach

Diagnostic sequence

  • Compare local and remote curl results; inspect listening ports and service logs to distinguish application failures from network timeouts.
  • Check security groups, route paths, load-balancer listeners/targets, source IP allow-lists, and relevant firewall/NAT behavior.
  • Make the smallest approved network change, then repeat the same tests from the original source and confirm application-level response.

Validation signals

Expected TCP reachability, successful endpoint response, healthy targets, and no unnecessary broadening of network access.

Evidence to attach: redacted command outputs and a simple request-path diagram.

05 / RESILIENCEAWS Backup · Lambda · SNS · S3

Backup & Recovery Operations

Designing an operationally clear backup workflow with monitoring and notifications so that recovery readiness can be checked, not assumed.

Define policy→Run backup→Notify status→Test restore
Read the engineering approach

Operational focus

  • Set backup scope, schedule, retention, and access boundaries according to recovery requirements.
  • Use automation and notifications where appropriate, with clear handling for failed jobs and missing signals.
  • Validate restore procedures periodically; a successful backup job alone does not prove that recovery will meet expectations.

Validation signals

Successful job history, visible failure notifications, protected backup access, and documented restore-test outcomes.

Evidence to attach: redacted backup policy, job status, notification example, and restore-test notes.

01 / OBSERVABILITYCloudWatch · S3

Designing a Reliable Log-to-S3 Workflow

Choose the log delivery path based on freshness, query needs, retention, and cost—not on the assumption that an ad-hoc query is a continuous export.

LogsRetentionIAM
Open the field notes

Decision checklist

  • Use CloudWatch Logs for active search and troubleshooting; select subscription delivery, scheduled export, or another supported pipeline based on the required latency.
  • Define the S3 prefix, encryption, bucket policy, lifecycle, and retention before enabling delivery.
  • Validate timestamps, multiline events, permissions, object arrival, and failure visibility with a known test event.

Evidence idea: a sanitized flow diagram and an example object path with account and customer identifiers removed.

02 / TROUBLESHOOTINGLinux · Networking

Read the Difference Between Refused and Timed Out

Different connection failures point to different layers. Test methodically before changing security rules or application configuration.

curlListenersNetwork path
Open the field notes

Diagnostic sequence

  • Connection refused often means the destination was reachable but no process accepted the connection, or an active reject occurred.
  • A timeout often indicates dropped traffic, an unreachable path, or a service that is not responding in time; verify the path rather than assuming the root cause.
  • Compare local and remote tests, confirm listening ports, then inspect routes, security groups, firewalls, load-balancer listeners/targets, and source-IP allow-lists.
  • After an approved change, repeat the same test from the original source and confirm an application-level response.

Safety rule: avoid broad CIDR or port openings as a diagnostic shortcut.

03 / DATABASERDS · MySQL

Investigate RDS CPU Spikes Before Resizing

Instance sizing is a workload decision. CPU alone rarely tells the whole story behind slow queries or periodic performance changes.

MetricsQuery patternsCapacity
Open the field notes

What to correlate

  • Compare CPU with freeable memory, connections, storage headroom, latency, and available database performance insights.
  • Align metric spikes with scheduler jobs, deployment windows, and query patterns before deciding whether the cause is capacity or workload.
  • For engine changes, review compatibility, release notes, backups, maintenance settings, a recovery plan, and post-change checks.

Evidence idea: a redacted before/after metric view with the time window and workload context explained.

05 / CLOUD COSTAWS · FinOps

Optimize Cloud Cost Without Guesswork

Cost optimization should preserve reliability and be based on utilization, usage patterns, and the operational requirements of each service.

Cost ExplorerUtilizationGovernance
Open the field notes

Practical review

  • Start with billing dimensions and usage trends to identify the services and workloads that drive spend.
  • Compare utilization with availability, scaling needs, licensing, storage growth, and recovery requirements before resizing or scheduling resources.
  • Review idle resources, unattached storage, snapshots, data transfer, log retention, and environment schedules where applicable.
  • Measure the change over comparable periods and record trade-offs; do not claim savings without a defensible baseline.

Evidence idea: a redacted cost comparison that excludes account identifiers and confidential billing details.

Make Infrastructure Changes Reviewable

Reusable infrastructure code is most useful when permissions, state, plans, approvals, and validation are treated as part of the design.

Controls worth keeping

  • Use separate environment inputs and reusable modules; keep secrets out of source control and protect remote state.
